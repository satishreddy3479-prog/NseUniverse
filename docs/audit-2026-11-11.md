# System audit, 11 Nov 2026

**What this audit is.** A section-by-section review done with the tools available without the production server: the full type checker, the linter, the whole test suites, dependency advisories, scans of the code for the usual production faults (blocking calls on the event loop, missing timeouts, unbounded caches, unsafe database settings), and a read of each section's scheduling and failure handling. **What it is not:** nothing here was observed on the running server, with live Kotak data, or in market hours; server logs were not available. Where a cause is inferred from code it says so.

## Section by section

### 1. Broker connectivity, stream, sampler
Read: reconnect bounds, status endpoints, the minute sampler. No change needed in code; the live behaviour (reconnects, stale detection) is covered by tests but was not watched live. **Open:** the "Stream: Stale" pill in the screenshots is shown whenever the feed has not pushed recently, which is correct outside market hours; it should be checked in a live session.

### 2. Storage (snapshots, observations, SQLite stores)
* Every store uses WAL except the snapshot index (`index.sqlite3`) and the in-memory day log. **Fixed:** the snapshot index now uses WAL and a busy timeout, so the option-chain page no longer waits behind a snapshot being written.
* All other stores already set a busy timeout (SQLite's own default is 5 s where none was set).
* No unbounded growth found in the stores themselves (the retention rules in `storage-plan.md` stand).

### 3. API layer
* The busiest endpoint, `GET /api/option-chain`, did its database read and response build **on the event loop**, blocking every other request while it ran. **Fixed:** it runs in a worker thread.
* Other `async` routes that touch no I/O (status, config) are fine; `market_refresh` awaits a coroutine, fine.
* The NSE trading calendar was re-parsed from JSON on every call of `GET /api/market/session` and in several services. **Fixed:** it is parsed once and shared.
* No network call without a timeout was found.

### 4. Intraday analysis service (rules-based command centre)
* **Memory leak found and fixed:** the cache of slow results (`_slow`) was keyed by values that change every minute (the stored row count, a research key), so entries accumulated for as long as the server ran. It is now bounded (the 48 newest are kept).
* The summary cache holds one entry (bounded). The feature and backtest caches are already bounded (`OrderedDict` with a maximum).
* mypy had flagged type suppressions hiding that mismatch; they are removed.

### 5. Intraday ML model: what it is and where it stands
See the dedicated section below, and the new panel on Market Intelligence.

### 6. Options tools (IV, skew, momentum, GEX, positioning)
Type findings in `volatility.py` (optional prices combined in arithmetic) were fixed by building the parity list from checked values; behaviour is unchanged (the existing hand-calculated tests pass). GEX server-versus-browser parity is covered by a fixture test.

### 7. Strategy builder, portfolio, automation
Type findings in `automation.py` fixed (`bool`/`float` returns). The stop/target/trailing rules are covered by tests; they are slow tests (the page tests wait for a code-split chunk), whose waits were given load headroom.

### 8. Swing trading
Read: paper book, live ledger, scan schedule. No defects found by the checks above. Not verified live (evening scan after 17:00 IST on the server).

### 9. Prediction (T+1, T+5, news, FII/DII)
Reviewed in this session's earlier work (D105, D107): holiday-aware inputs, US-holiday-aware freshness, ledger-based recording, data-aware refresh schedule, hourly headlines, FII/DII masking bug. Remaining structural risk: NSE's FII/DII feed and NSDL keep one day only, so a missed evening is only recoverable by CSV import.

### 10. Market Intelligence
Five evidence groups, no double counting, proxies labelled, validation framework, heavyweight engine (D102-D104). New in this audit: the intraday ML research panel (below). Not yet observed on the server in market hours.

### 11. Server management, deployment
Read: update/rollback logic and the management helper design. The documented rule "do not put the backend behind a reverse proxy until control endpoints are authenticated" conflicts with the deployed Caddy setup described in `deployment-server.md`: `proxy_headers=False` is set so every request appears to come from loopback, which means **the loopback trust of the control endpoints is only as strong as the proxy's login**. Verify on the server that the proxy requires sign-in for `/api/*` control routes. This was not checked here.

### 12. Frontend
* **First-load size:** the secondary pages (Market Intelligence, Portfolio, Settings, Diagnostics, Server Management, Data clean-up) are now code-split like Analysis, Prediction, Swing and the Strategy Builder; the entry chunk is about 330 KB (was about 610 KB), with the charting library only loaded by pages that draw charts.
* Menus: one FNO Tools menu, Swing trading as a main section, a phone accordion (D106). NEW badges removed.
* Daylight theme rebuilt (D106) and then re-tuned for the same vibrancy as the dark theme: a cool paper page, white cards, deep-navy ink, data colours in the dark theme's hues.
* Accessibility: buttons carry names and `aria-expanded`; focus outlines are kept; the phone status pill keeps its words for screen readers.

## The intraday ML model
**What exists:** a research pipeline, not a deployed predictor (`docs/intraday-ml-plan.md`, `docs/intraday-engine-status.md`, `app/intraday/{dataset,labels,evaluate}.py`).
1. After each finished session the end-of-day job turns every minute into a row of features (price path, options, implied volatility, futures VWAP/flow/depth, breadth, breakout state), built only from samples at or before that minute (tested), and a label: whether NIFTY next touched an up barrier, a down barrier or neither within the horizon (barrier = k x daily standard deviation x sqrt(h/375)).
2. `walk_forward` tests, on later sessions only, a regularised logistic model against baselines (majority class, momentum state, opening-range state, VWAP state) with log loss, Brier score and calibration error, and tests whether each feature group adds anything to price alone.
3. A gate withholds every probability until the model beats the best baseline in at least 60 % of test sessions, with a sign-test p of 0.05 or less, a mean log-loss gain of at least 0.005, calibration error at most 0.05 and 60 labelled sessions. The stage ladder: collecting (0), experimental (5), paper-testing (20), eligible for "validated" (60).

**How it has performed:** the server's results were not available to this audit, and no evaluation result is stored anywhere I could read (the evaluation was computed on demand and kept in memory only). On the local machine there are no labelled sessions. Therefore no performance figure is claimed here. By design the expected state at this stage is "insufficient" or "experimental": a few sessions behind it, results are close to noise.

**Integrated into Market Intelligence:** a new panel shows what the model does, the stage and number of labelled sessions, the last evaluation (each model's log loss, Brier score and calibration error against the baselines, the log-loss gain, the gate's verdict and its reasons, and whether each feature group helps), and when it last ran. The evaluation now runs by itself once per session day after 15:45 IST (never in market hours, never twice at once) and its summary is stored (`data/intraday_ml_digest.json`), so the page reads a small file. **It is not part of the sentiment score**, and no probability is shown until the gate passes; the capability list marks it PARTIAL (research only). If the gate ever passes it will be shown as context first, not scored, until the forward record justifies more.
